# Product walkthrough and demo script

Use the [quickstart](QUICKSTART.md) first. State the active mode before showing
results: **seeded UI**, **synthetic backend**, or **live corpus and providers**.
Only the last mode demonstrates actual research. The same review workflow helps
inspect all three; exact results depend on evidence, configuration and mode.

## Walk through a case

1. Open the case board. In mock mode choose a seeded glucose-sensor case for a
   repeatable tour. In HTTP mode choose **New case** and enter a fictional,
   permitted request such as:

   > A fictional European company develops wearable glucose sensors. It wants
   > R&D partners in Bern for sensing algorithms and evaluation methods.
   > Find relevant research capabilities, groups and infrastructure. Distinguish
   > direct evidence from adjacent opportunities. Do not assume that any group
   > is available for collaboration.

   The built-in **Glucose sensor** example is also available. Its operator lead
   about DCB is a hypothesis to verify, not a fact to repeat without evidence.

2. Select **Search** and inspect progress. If blocking clarification appears,
   answer it in the chat. State missing intent explicitly; do not supply guessed
   public research facts as if they came from the company.
3. Read the reason cards, result categories, direct/adjacent labels and coverage
   caveats. Where a person, role, facility or contact is absent, leave it unknown.
   A unit-only result can be useful without inventing a named expert.
4. Open a citation/source. Compare the exact quotation and original URL with the
   displayed assertion. Distinguish **Pinned corpus** and **New case research**.
   Source status and relevance are separate from semantic support.
5. Review every reason using keep/reject, retaining at least one. A rejected card
   is editorially excluded; it is not a declaration that its source is false.
6. Select **Export**, approve the exact current report/selection when requested
   and download PDF. Verify that the export contains kept reasons and citations
   and excludes rejected cards. PPTX appears only when supported by the mode.
7. In chat choose **Rewrite existing report** for a wording-only request, such as
   “Make the existing reasons shorter for a company executive; retain caveats.”
   This reuses the frozen evidence pack and reassesses the wording.
8. Choose **Research / change focus** to request a different capability. This
   starts a new input/research revision. Browse history; historical reports are
   read-only. Changed content/support requires review again.

For a seeded tour, use the existing scripted examples; arbitrary chat may not
produce new behavior. For live research, do not expect the same named matches or
latency each time. A short, honest partial report is a valid demonstration.

## Useful challenge checks

Try the **Out of scope** example (“Grain trading company looking for commodity
partners in Bern”). Inspect the coverage limitation instead of expecting medical
matches. Compare lay wording such as “glucose sensor” with “continuous glucose
monitoring”; assess the retrieved evidence rather than assuming synonyms guarantee
identical results. Reopen after a reload: HTTP mode requires reconnecting, while
server runs continue.

Do not add fictional demo cases to own-case comparison memory. Manual company
plans, when enabled, require permitted operator input and confirmation. They are
attributed plans, not model-generated forecasts.

## Suggested video outline: at most two minutes

- **0:00–0:15:** Introduce Stregoni, B2B, the operator and the fragmented-source
  problem. State whether this recording is live or uses fixtures.
- **0:15–0:35:** Show permitted company needs and the research/clarification flow.
  If research is prerecorded or accelerated, label the cut.
- **0:35–1:10:** Inspect a reason, exact passage, URL, match type and limitation.
- **1:10–1:40:** Review cards, keep/reject and download the brief.
- **1:40–2:00:** Explain the value and the current boundary: partial coverage,
  unmeasured retrieval quality and proposed offline deployment.

The template caps the demo video at two minutes; it does not establish the
live-pitch duration. Video URL and hosted judge access remain
